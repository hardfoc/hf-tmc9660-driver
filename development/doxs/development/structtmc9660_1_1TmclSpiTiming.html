Detailed Description

Timing of the parameter-mode SPI request/reply handshake.

What the vendor documents (TMC9660 Parameter Mode Reference Manual Rev. 0, section "Serial-Peripheral Interface", Tables 3–5; TMC9660 datasheet "SPI Peripheral — Electrical Characteristics"; both PDFs are in docs/datasheet/):

  • The reply to a 64-bit request is clocked out during the next SPI datagram.
  • SPI_STATUS_NOT_READY (0xF0) in byte 0 means the chip is still processing. The manual says the reply in that datagram is not the reply to the processed command, the command in that datagram is ignored, and the datagram should simply be re-sent until the status goes away.
  • The only inter-datagram timing that is specified is CS_ high time tCSH ≥ 4 × T_CLK (about 100 ns at the 40 MHz system clock) and fSCK ≤ 10 MHz. No minimum processing time or turnaround time for a TMCL request is given.

The protocol therefore needs no blind delay: the ready indication is the NOT_READY status, and polling it is the documented way to wait. The defaults below follow that rule: no frame gap, then re-send with a short exponential back-off (pollIntervalUs doubling up to pollIntervalMaxUs) for at most maxPolls re-sends. With the defaults the worst-case wait is 20+40+80+160 + 56×200 µs ≈ 11.5 ms, the same order as the previous fixed 50 × 200 µs budget, which is only acceptable from thread context.

frameGapUs is kept for buses or firmware revisions that need a settle time between the request and the next datagram; set it from a measurement (see the tmcl_timing example), not from a guess. Releases up to 1.0.0 hard-coded 1000 µs here (see legacy()).
