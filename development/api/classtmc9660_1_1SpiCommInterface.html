Detailed Description

template<typename Derived>
class tmc9660::SpiCommInterface< Derived >

CRTP-based SPI implementation of TMC9660CommInterface.

Uses a 4-wire SPI bus (mode 3) to exchange 64-bit datagrams (8 bytes). Data is sent MSB-first, big-endian. Replies match the previous command; initial reply uses FIRST_CMD status.

This template class uses CRTP for compile-time polymorphism, providing zero runtime overhead.

Example usage:

class MySPI : public tmc9660::SpiCommInterface<MySPI> {
public:
CommMode mode() const noexcept { return CommMode::SPI; }
bool spiTransferTMCL(...) { ... }
bool spiTransferBootloader(...) { ... }
bool gpioSet(...) { ... }
bool gpioRead(...) { ... }
void debugLog(...) { ... }
void delayMs(...) { ... }
void delayUs(...) { ... }
};

Exchange one TMCL datagram over SPI using the two-transaction reply protocol.

Parameter-mode SPI is pipelined: the reply to a command is not clocked out during that command's own transaction, but during the next one. A single logical request therefore costs two 8-byte transactions:

  1. Transaction 1 clocks out tx. The bytes received back belong to whatever command preceded it, and are surfaced through first_reply. If they carry NOT_READY, the chip ignored tx (reference manual, SPI section), so tx is re-sent; this cannot duplicate a write because the ignored copy was never executed.
  2. Transaction 2 clocks a reply-request frame to shift out the reply to tx. Unless second_command is supplied this is opcode 0xFF with all other fields zero (wire bytes FF 00 .. 00 FF), matching ADI's tmc9660_param_sendCommand_SPI.

Between the two transactions the driver waits TmclSpiTiming::frameGapUs (default 0 µs: the vendor documents no processing time, only the NOT_READY handshake). Transaction 2 is then re-sent with a doubling back-off while the reply is NOT_READY or not yet valid (status 0x00, bad checksum, or — with TmclSpiTiming::verifyReplyOpcode — an opcode echo that does not match tx), at most TmclSpiTiming::maxPolls times.

When Derived exposes hostSpiTransferTMCLPair() that primitive clocks both transactions inside a single bus reservation (required on shared buses where a peer may re-program the SPI mode between the frames) and receives the gap as an argument.

Parameters
txTMCL command frame to transmit.
replyReceives the reply to tx (parsed with tx opcode/type context, so multi-frame replies such as GetVersion decode correctly).
first_replyOptional out-param capturing the reply carried by transaction 1, i.e. the answer to the previous command. Pass nullptr to drop it.
second_commandOptional frame to use in place of the 0xFF reply-request, letting a caller pipeline the next command into transaction 2. Prefer transferTMCLBatch(), which also collects that command's reply. A transaction 2 that comes back with a stale (not NOT_READY) reply is re-sent, so second_command must be idempotent.
Returns
true if a well-formed reply to tx was parsed; false on bus error, or when the reply was still not ready or not valid after the poll budget.
Warning
Do not substitute an all-zero frame for the 0xFF reply-request. The chip parses opcode 0 as a real (invalid) command and queues a checksum-error reply while the requested reply is being shifted out, which corrupts the value bytes.
Note
The address parameter is UART-only and is ignored here.

Pipelined batch: requests.size() TMCL accesses in N + 1 SPI datagrams.

Datagram k carries request k and clocks out the reply to request k − 1; the last datagram is the reply-request 0xFF that clocks out the reply to request N − 1. Compared with N calls of transferTMCL() this saves N − 1 datagrams and N − 1 handshakes. Correctness rules:

  • First element: the reply carried by datagram 0 belongs to whatever preceded the batch and is discarded.
  • Last element: its reply is collected with the trailing reply-request datagram.
  • NOT_READY: the datagram just sent was ignored by the chip and is re-sent after the back-off; no request is skipped or duplicated.
  • Stale reply (status 0x00, bad checksum, wrong opcode echo): it is not known whether the request in that datagram was executed. The previous request is re-issued as a single transferTMCL() and the pipeline restarts at the current request, which may therefore execute twice. Only pass idempotent requests (SAP/GAP/SGP/GGP, RamDebug reads). TmclSpiStats::recoveries counts these events.
Parameters
requestsFrames to send, in order.
repliesReceives one reply per request (same index). Must be at least as long as requests.
addressUART-only module address; ignored here (signature parity).
completedOptional: number of leading elements whose reply is valid when the function returns (equals requests.size() on success).
Returns
true if every request got a well-formed reply. Each reply still carries its own TMCL status; check TMCLReply::isOK() per element.
